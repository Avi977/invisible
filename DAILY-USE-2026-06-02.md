## How to use it daily (single command)

```bash
cd ~/.invisible
./bin/invisible-launch
```

That's it. The launcher:
- Spawns `invisible-dashboard` (:8765), `invisible-frontend` (:8090), `invisible-pty` (:8091)
- Verifies each port binds (5 sec per daemon)
- Opens your default browser to http://127.0.0.1:8090/
- Stays in foreground; **Ctrl-C kills all 3 daemons cleanly** via signal trap

Alternates:
- `./bin/invisible-launch --no-browser` — daemons only, you open the URL manually (good for tmux / SSH)
- `./bin/invisible-launch --port 8090` — change frontend port if 8090 is taken
- `./bin/invisible-quit` — idempotent stopper, kills daemons by both port and process name

The launcher currently keeps `INVISIBLE_HOME=$PWD`, so you can run it from any project's invisible.toml setup, not just `~/.invisible`.

## Bugs found + fixed while driving

Both surfaced from tonight's M2 PR merges. Both committed.

### `cc2f168` — frontend/data.jsx `ANALYTICS` + `TOOL_WORKFLOWS` undefined refs

`Object.assign(window, { ANALYTICS })` referenced a symbol that the analytics-aggregator workstream had deleted (the mock was replaced by `/api/v1/analytics` fetch). My PR-merge resolution re-introduced the `Object.assign` without restoring the `const`. Same pattern for `TOOL_WORKFLOWS` from tools-page. Threw `ReferenceError` on initial load — **every page broke until this was fixed**. Two-line delete.

### `cc2f168` — lib/api/tree_local.py SSE missing CORS

`_send_sse_headers` had a stale comment ("Cross-origin CORS headers are supplied by the dashboard handler's `end_headers()` override"). But after tools-page PR #10's CORS refactor, `end_headers()` is bare — CORS now flows through `handler._cors_headers()` called from `_send_json` / `_send_text` / `_send_html`. The SSE path never went through any of those, so the EventSource subscription on the Folders page was blocked: `No 'Access-Control-Allow-Origin' header is present on the requested resource`. Added `handler._cors_headers()` before `end_headers()` in `_send_sse_headers` (same single-source loopback-echo pattern). Folders SSE watch stream now subscribes cleanly (verified twice in network log).

### `61113e3` — bin/invisible-launch + bin/invisible-quit

Not a bug fix — a deliverable. Daily-use one-command entry point with clean teardown.

## Honest gap: Tauri shell shows mock data

**Invisible.app launches but renders the same mock data the M1 sessions started with.**

Why: the M1/M2 workstreams wired `frontend/` (the Babel-standalone build served by `bin/invisible-frontend`). The Tauri shell loads `frontend-vite/dist/` (Vite-bundled production build). The Vite version is structurally different — it uses ES module imports of `Data.jsx` which still exports `ANALYTICS`, `TOOL_WORKFLOWS`, etc. mocks. **No M1/M2 workstream migrated these to fetch from /api/v1/.**

Evidence: `strings frontend-vite/dist/assets/*.js | grep "/api/v1/"` returns 0 hits.

This is the natural next phase — the Tauri shell needs its own page-by-page wiring migration. It's NOT a regression from tonight; it's the M1.5 / M3 work that's been deferred since the Tauri shell shipped (PR #4 / PR #7).

**Operationally:** for daily use, run `bin/invisible-launch` and use the browser. If you double-click Invisible.app, you'll see mock pages — treat that as a preview of the production binary's shell, not the working app.

A pragmatic path to make Invisible.app work daily: modify it to point its webview at `http://127.0.0.1:8090` and bundle `bin/invisible-launch` as a sidecar. ~half a day of work; not in scope tonight.
